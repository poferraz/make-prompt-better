# Project audit and implementation plan

Audit date: 2026-11-06, America/Vancouver. **Recommendation: fix the installation boundaries, evaluation provenance, and assurance claims before a broad release promotion.** Source installation and the deterministic tooling are real and testable. The project has working CI and useful historical evidence, but a green build does not establish that the optimizer improves every prompt, preserves every requirement, or safely runs in every host.

The user removed the event-related scope during the audit. This report therefore uses release milestones, not an invented submission deadline. No application code, canonical instructions, configuration, tests, dependency files, releases, repository settings, or outreach were changed. The only repository additions are this draft and the [separate technical review](../code-security/2026-11-06-ed95968.md). The user-mandated installer verification resynchronized seven existing, byte-identical local skill copies after a complete-tree comparison.

## Product, skill, research, and GitHub findings

### PR-01: The first visual still advertises unavailable installation and stale uplift

**P1, verified source and rendered page.** [assets/hero-banner.svg][hero] line 145 says `npx make-prompt-better init`; line 201 shows `+27.3%`; line 226 shows `94.1% Frontier Win Rate`; line 137 says to compile prompts into proofs. [README.md:22,40][readme] says the current version has not been remeasured and npm is unpublished. Its historical frontier win rate is 86.1% at line 257. Registry 404 and the rendered desktop hero confirm the contradiction reaches users. The release checker only checks the hero's version string (`scripts/check-release.py:24`).

**Impact:** the most prominent installation path fails and the visual suggests stronger assurance than the product provides. **Cause:** marketing assets are outside semantic release checks. **Target:** one working source-install route, no unqualified uplift, and language about evidence/verification rather than proof. **Acceptance:** every installation string in README, SVGs, CLI help, release notes, and package metadata is executable for its declared distribution; every numeric claim links to its version/protocol/sample. **Dependencies:** W04 before W07; low implementation risk, high trust impact.

### PR-02: Research attribution is present, but some rules exceed or outlive the sources

**P1, high confidence on the documented mismatches; full corpus validation remains partial.** [SKILL.md:10-26][skill] and `CLAUDE.md:5` call the corpus eleven peer-reviewed papers. The corpus actually has eleven principle groups and at least fourteen distinct arXiv IDs because HARNESS bundles four papers. Some arXiv records show proceedings/acceptance; all-fourteen peer-review status was not established.

Three consequential checks:

1. [Gloaguen et al. (2026), v3, sections 4.2 and 4.4](https://arxiv.org/html/2602.11988v3) reports average decreases of 0.5% and 2% with no significant accuracy effect, and no significant effect from individual instruction categories or file length. This does not support the README's unqualified statement that generated context files are proven to lower success by 3%, or that a particular four-pillar pruning recipe reliably improves it. Earlier-version observations should be versioned, not silently treated as current universal laws.
2. [Yin et al. (2026), @skills v1](https://arxiv.org/html/2608.12610v1) supports the discussion of skill residency and attention limits. The fetched full text contained no matches for `negative`, `prohibitions`, `predicate`, or `backfire`. The attributed experimental claim that prohibitions backfire under competing incentives could not be located. Its support is UNKNOWN until an exact experiment/page or different source is supplied; the positive-recipe rule can remain an explicitly labeled project design choice.
3. [Shao et al. (2026), Context Language Models](https://arxiv.org/abs/2609.37725) reports its 11.4% accuracy and 21.5% FLOP result on BrowseComp-Plus. `README.md:84` associates these numbers with the project's context-file/scratchpad advice. [Lee et al. (2026), Meta-Harness](https://arxiv.org/abs/2603.28052) evaluates harness-code search, not this repository's exact code-first template or its 25% commentary cap. These are useful inspirations but their effect sizes are not measurements of this skill.

Other stale assurance appears in `docs/methodology.md:13` (a reliable approximately 26% improvement) and `docs/tradeoffs.md:136` (all four failures resolved in v4.3.0), while README correctly admits no fresh v4.3 measurement. `README.md:92,121` uses creative typicality `p <= 0.15`; the skill and template use `p <= 0.20`. These probabilities are heuristic model estimates, not calibrated guarantees.

**Impact:** researchers and careful users cannot distinguish empirical findings, historical observations, and the author's adaptations. **Cause:** duplicated claim text without a versioned claim ledger. **Target:** claim/source/version/table/task scope/limitation/adaptation records. **Acceptance:** each public effect size has a traceable original measurement; no blanket peer-review claim or transferred effect size; unsupported attributions marked unknown or removed from promotional claims. **Dependencies:** W04, then W05/W07. Do not change the user's architectural invariants during this audit.

### PR-03: Historical benchmark reproducibility is stronger than current efficacy evidence

**P1 before benefit claims, verified.** The aggregate regenerated byte-equivalent JSON in a temporary copy: 14 models and 164 pairs; 36 in-session pairs with mean delta +2.3611/25, 128 isolated pairs with -2.3477/25. Those are saved subjective rubric results, not new live inference. README identifies different protocols and negative results near the top, which should be preserved.

The runner's fixed suite has one prompt per domain; sampled model identities, repeated observations, self-preference, incomplete runs, and historical label leakage remain limitations. Cluster bootstrap code cannot remove those design confounders. The current `--unprescribed-routing` and `--judge-model` flags are implemented features; their existence does not establish a controlled v4.3.0 result. CS-04/05 must be fixed before a new experiment can support public claims.

**Target and acceptance:** predeclare a bounded evaluation, keep baseline/optimizer/judge provenance, include requirement retention and harmful additions as direct outcomes, record actual latency and full token/call cost, include negative cases and independent human checks, and publish failures alongside successes. No minimum positive uplift is an acceptance criterion. **Dependencies:** W03 and W04 before W08. Compute cost and host availability remain unknown.

### PR-04: The first-use journey lacks a complete reproducible example

**P2, verified docs/CLI and static host boundary.** `README.md:36-38` leaves invocation to the host; the prompt refers to an attached diff that is not provided. The "5-Second Diff" at lines 54-58 describes desired behavior rather than showing an actual compiled prompt and an observed result. The file named `live-3d-demo.svg` is an animated illustration, not a captured execution. CLI help still uses registry commands, and there is no `optimize` subcommand. The documented rejudge example uses unsupported `--strip-markers`, which returned exit 2; `--strip-cert-markers --dry-run` returned 0 and loaded 128 pairs.

The installer copies the full skill into `.cursor/skills/...`, but the generated `.cursor/rules/...mdc` contains skill-root-relative `references/...` paths without sibling references. Whether Cursor resolves them successfully is UNKNOWN without a host test. Supporting a path is not supporting a complete interaction.

**Target:** source install, discovery, one complete sample input, expected preservation checks, observed output with version/model provenance, a next action, and uninstall/restore instructions. **Acceptance:** a fresh user succeeds in one explicitly tested host, can identify an unexecuted output, and can remove or restore the installation without touching other tools. **Dependencies:** W01/W02/W05 before W07/W08.

### PR-05: Visual polish masks readability and accessibility gaps

**P2, rendered desktop and 390x844 inspection plus SVG source review.** The dark palette, consistent typography, and visual mode grouping provide a coherent identity. At a 390px viewport, the dense hero's command and certificate labels become tiny; the before/after table extends well below the viewport with narrow text columns. Six badges wrap into multiple rows before the first-use explanation. The full README is 331 source lines and repeats mode and claim tables.

All four SVGs already contain `prefers-reduced-motion` rules, a useful control. They also contain infinite animation loops; no direct pause control was established in the rendered embedded images. This is a review concern under [W3C's pause/stop/hide guidance](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html), not a blanket WCAG conformance verdict. Alt text mostly names the diagram rather than conveying its full informational content. Contrast, assistive-technology navigation, and reduced-motion behavior in each actual browser remain untested.

**Target:** keep the visual identity but make Markdown the authoritative, readable content. Use a short static hero, one input/output example stacked vertically on narrow screens, optional expanded evidence, and a linked animation/video with transcript. **Acceptance:** essential instructions are ordinary selectable text, readable at 390px and 200% zoom; no essential information depends on animation/color; reduced-motion/static versions retain all information. **Dependencies:** truthful copy in W04; implement in W07, with human usability checks in W08.

### PR-06: Adoption potential is a testable hypothesis

These counts do not prove failure, virality, or product-market fit.
