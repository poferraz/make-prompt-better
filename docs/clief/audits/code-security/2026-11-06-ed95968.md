# Code, security, and verification audit

Audit date: 2026-11-06, America/Vancouver. This is a report, not a remediation change or an approval. The [project audit and implementation plan](../icm/2026-11-06-ed95968.md) is the navigation entry point. Findings here are outside Clief core authority and must never be applied through `clief-apply`.

## Consequential findings

Urgency is an engineering judgment based on the demonstrated impact: P1 means repair before the next promoted release or affected benchmark run; P2 means the next maintenance cycle. No P0, CVSS score, or blanket security certification is asserted. Confidence distinguishes an executed reproduction from static evidence. All malicious-looking filesystem scenarios used disposable, auditor-owned files.

### CS-01: A runtime-specific project operation modifies Cursor files

- **P1, high confidence, EXECUTED.** Affected boundary: selected runtime versus unrelated project configuration.
- **Evidence:** [install.sh:123-153][installer] writes/removes the Cursor rule; line 213 calls it whenever `SCOPE == project`, irrespective of the selected runtime. A temporary `--project --runtime claude` install overwrote a pre-existing Cursor rule. The corresponding Claude uninstall deleted that rule. Both returned 0. `--backup` is implemented for skill directories, not this rule.
- **Failure path:** a user chooses Claude in a repository that already has `.cursor/rules/make-prompt-better.mdc`; the operation changes another tool's user-owned configuration. This also happens on explicit project installs for other runtimes.
- **Cause:** scope and runtime selection are conflated in the Cursor adapter condition, and rule ownership is not tracked.
- **Improvement:** build an explicit target plan before mutation; include Cursor output only when Cursor is selected. Preserve an existing rule unless its managed identity is established or replacement is explicitly requested. Scope uninstall to artifacts owned by the selected installation.
- **Acceptance:** installing and uninstalling every non-Cursor runtime preserves an unrelated Cursor sentinel byte-for-byte. Cursor installation has its own backup, conflict, and uninstall tests. See W01 in the main plan.

### CS-02: Cursor output follows an existing file symlink

- **P1, high confidence, EXECUTED.** Affected boundary: intended rule destination versus another file writable by the current OS user. External review standard: [CWE-59, improper link resolution](https://cwe.mitre.org/data/definitions/59.html).
- **Evidence:** [install.sh:143-152][installer] redirects generated text directly into `mdc_file`. In a temporary project, that path was a symlink to an owned sentinel outside `.cursor`. Running `--project --runtime cursor --backup` changed the sentinel, left the link intact, produced no rule backup, and returned 0.
- **Threat precondition:** an attacker or another process can arrange a project rule symlink before the user runs installation. This demonstrates a same-user file overwrite, not a remote or privilege-escalation exploit.
- **Improvement:** explicitly handle final-component and ancestor symlinks, validate destination containment, and write to a new sibling temporary file before a controlled replacement. A simple `realpath` check followed by an unchecked write is not sufficient against a race.
- **Acceptance:** symlinked rule destinations, dangling links, and links in parent paths cause a clear refusal or a documented safe operation. External sentinel contents remain identical. Normal source symlink installation remains a supported, separately tested behavior. See W01.

### CS-03: Failed updates lose the previous installation

- **P1, high confidence, EXECUTED.** Affected boundary: persistent local skill data and recovery.
- **Evidence:** [install.sh:194-207][installer] removes the old target before copying/linking the replacement. Backups are opt-in and timestamped to the second. A probe installed a local customization, made only `cp` exit 23, and observed exit 23, no target, no original customization, and no backup.
- **Impact:** an interrupted update can leave the skill unavailable and permanently remove local edits. Existing tests prove a subsequent clean installation can succeed; that is different from preserving the previous state. [tests/test_more_integration.py:57-94][integration-more] verifies backup retention only when backup was requested.
- **Improvement:** stage and validate the complete replacement before switching targets. Preserve the previous target through failure and make ownership/conflict handling explicit. Use collision-resistant backup names, a transaction journal where needed, and interruption cleanup that retains the last usable state.
- **Acceptance:** injected failures at mkdir, copy, validation, rename, link, and rule generation preserve the previous usable tree or provide a documented intact backup and deterministic restore. Repeat and concurrent operations cannot collide or nest backups. See W01.

### CS-04: Benchmark resume is not bound to the experiment

- **P1, high confidence, EXECUTED plus STATICALLY REVIEWED.** Affected boundary: old experiment evidence versus a newly requested evaluation.
- **Evidence:** [run_ollama_benchmarks.py:469-506][runner] chooses output paths only by model slug, loads existing JSON, and skips by test IDs and report presence. It does not match skill content, prompt suite, code revision, seed, judge, anonymization, swapped order, or routing configuration. The README's first controlled-run example targets two models with already-complete tracked results.
- **Reproduction:** copied the real `gemma4-31b-cloud` results into a temporary root; supplied a changed skill string, an independent judge, seed 999, native routing, and swapped judging. The function returned `True`, made zero model calls, printed `[SKIP] Requested tests and final report already exist.`, and left saved bytes unchanged.
- **Related static evidence:** lines 485-487 replace top-level judge/routing fields on loaded data before later partial saves. A partial resume can therefore label mixed old/new test records with new top-level metadata. `aggregate_results.py:168-169` reads top-level judge metadata. Existing saved metrics say `version: 4.0.0` while current summaries describe the historical v4.2 protocol, illustrating why a version string alone is inadequate. This audit did not rewrite or reattribute those records.
- **Impact:** users can believe they reran v4.3.0 under a new protocol while actually reading older outputs; partial runs can mix experiments. `--no-resume` currently reuses the same directory and can overwrite historical evidence.
- **Improvement:** immutable run IDs, a complete hashed run manifest, explicit result directories, and strict resume compatibility. Preserve legacy artifacts as legacy; reject mismatches before any model call or write. Do not recommend `--no-resume` against the tracked results directory as a workaround.
- **Acceptance:** changing any experiment-defining field produces a new run or a clear mismatch failure. Identical manifests resume only missing stages. Partial and mixed-protocol inputs cannot silently receive a homogeneous provenance label. See W03.

### CS-05: Eight prescribed domain-template mappings are wrong

- **P1, high confidence, STATICALLY REVIEWED with deterministic comparison.** Affected boundary: benchmark instructions versus the skill being evaluated.
- **Evidence:** [run_ollama_benchmarks.py:98-188][runner] supplies the required template at lines 526-529. Compare the numbered headings in [domain-templates.md][templates].

| Test | Domain | Prescribed template | Current matching template |
| --- | --- | --- | --- |
| 2 | Financial analysis | 2 | 9 |
| 3 | Medical reasoning | 3 | 7 |
| 4 | Legal analysis | 4 | 8 |
| 5 | Research synthesis | 5 | 3 |
| 6 | Business decision | 6 | 5 |
| 7 | Compliance | 7 | 4 |
| 8 | Document analysis | 8 | 2 |
| 9 | Comparative analysis | 9 | 6 |

- **Impact:** the default forced-routing experiment gives conflicting domain and template instructions. It cannot cleanly test the intended current template. This comparison does not establish the actual causal contribution to historical model scores.
- **Improvement:** stable template identifiers and one checked mapping; treat forced routing and natural routing as distinct protocols. Preserve old results and document their actual inputs.
- **Acceptance:** every prescribed template exists and matches its domain; all 12 test mappings are checked; natural routing emits no prescribed template. See W03.

### CS-06: Linter advice conflicts with requirement preservation and overstates assurance

- **P1, high confidence, EXECUTED.** Affected boundary: heuristic detection versus users' decision about prompt quality.
- **Evidence:** [scripts/lint-prompt.mjs:69-106][js-linter] flags output ordering and demo context without understanding their role, then recommends mandatory evidence-first presentation and removing downstream stakes. [lint_context.py:153-170][py-linter] has analogous behavior. Both conflict with the exceptions in [SKILL.md:48,77-78][skill]. Both label high scores `Certified` and `Production-Ready` (JS lines 140-148; Python lines 206-215).
- **Reproduction:** `Prepare a briefing for tomorrow's client demo. State the final answer first, after checking the evidence. Preserve the deadline and budget.` triggered ORDER-02 and LEAKAGE-04. An empty file received `100/100`, `A (Certified)`, and no findings from the JS linter. Those are observed tool outputs, not this audit's scores.
- **Impact:** literal fixes can delete requested ordering or context. A successful static lint can be mistaken for factual correctness, safe code, or complete requirements, none of which these regex checks establish.
- **Improvement:** describe matches as heuristic signals, preserve requested requirements, distinguish inference order from presentation order, support declared profiles/exceptions, and replace assurance language with observational status. Add an explicit empty-input state. Keep the numeric heuristic only if its unvalidated meaning is clearly described.
- **Acceptance:** deadline and summary-first examples are not instructed to discard those requirements; exact-match negative examples still report signals. Empty text cannot be certified. Tests cover quoted examples, code fences, all supported profiles, and both linters' intended differences. See W02 and W05.

### CS-07: CLI process and option failures can look successful

- **P2, high confidence, EXECUTED.** Affected boundary: command invocation versus automation status.
- **Evidence:** [bin/cli.mjs:55-56][cli] uses `res.status ?? 0`. A temporary PATH without Bash produced exit 0 and no output for `init --dry-run`; no installation occurred. Lines 66-67 discard every dash-prefixed argument, so `lint --strict` was silently accepted. Findings always exit 0 at line 88. This is an informational linter today, not an enforced CI policy.
- **Impact:** scripts can report success when the installer never ran; typoed options do not protect users as expected. Paths beginning with a dash have no documented `--` handling. Direct read errors such as directories can produce raw stack traces.
- **Improvement:** handle `error`, signal termination, and null status explicitly; use one strict argument parser; reject unknown switches; support `--`; keep informational default behavior but offer a documented opt-in failure threshold with meaningful exit codes.
- **Acceptance:** missing Bash and spawn failure return nonzero with actionable text; unknown flags fail; known flags and dash-prefixed paths work; clean lint and findings follow the documented status policy. See W02.

### CS-08: Benchmark persistence and queue status do not support reliable recovery

- **P2, high confidence, mixed EXECUTED/STATICALLY REVIEWED.** Affected boundary: long-running evaluation, persisted evidence, and shell orchestration.
- **Evidence:** [runner:658-681][runner] saves only after the full test and writes JSON directly. A failure during judging loses earlier generation work; interruption during write can truncate the sole checkpoint. The second swapped judge response is computed at 608-616 but only `eval_res` is persisted at 672. [rejudge_saved_outputs.py:191-232][rejudge] keeps records in memory and prints a summary without a resumable raw-response artifact. [run_benchmarks_queue.sh:78-114][queue] uses `--no-resume`, suppresses aggregation failure with `|| true`, and has no final nonzero exit for failed models.
- **Reproduction:** an isolated copy of the queue with a fake Python executable returning 17 and a no-op sleep printed `Successful models: 0/11` and still exited 0. No cloud service was contacted.
- **Impact:** lost paid work, irreproducible judge decisions, false automation success, and overwritten historical results. No end-to-end cost budget or bounded streamed-response size is implemented. The socket timeout is not a whole-experiment deadline.
- **Improvement:** per-stage atomic checkpoints with both judge passes and mappings; bounded retries and cancellation; explicit budgets/dry-run call counts; append-only failure records; checkpointed rejudging; aggregate and model failures reflected in queue exit status. Keep prompts private by default and disclose where API requests and result files go.
- **Acceptance:** interruption after each stage resumes without repeating successful stages; both judge responses reproduce final scores; invalid JSON is quarantined; queue fails when any required model or aggregation fails. See W03.

### CS-09: Local verification and distribution contracts have gaps

- **P2, high confidence, STATICALLY REVIEWED and existing tests EXECUTED.** Affected boundary: contributor expectations, installed package, and CI.
- **Evidence:** `package.json:22-25` omits `tests/` integration coverage from `npm test`; CI does run it. `pyproject.toml:12-25` declares Ruff, mypy, and pytest settings without a corresponding enforced lint/type command in workflows; this is configuration, not executed evidence. Workflows use Node/npm from mutable runner images without `setup-node`; the recurring matrix only runs on a PR when its own YAML changes (lines 7-10), leaving normal product changes to Ubuntu primary checks and later scheduled cross-platform checks.
- **Packaging:** the actual npm archive integration test passes; however `package.json:11-20` excludes `assets/` and `docs/` referenced by its packaged README, and includes broad `scripts/` that contains source-only benchmark launchers whose research dependencies are absent. No `engines.node` or tested minimum Node version is declared. These are optional-publication blockers, not evidence that source installation is unavailable.
- **Impact:** contributors can run the advertised command and omit installer regressions; packaged help/docs can send users to absent resources; tool availability varies across runner updates.
- **Improvement:** one explicit verification entry point, deliberate platform/Node matrix, focused package allowlist, archive link checks, and source-versus-registry documentation. Do not add runtime dependencies just to satisfy a linter preference.
- **Acceptance:** documented fast/full commands match actual coverage; archives include or link to all advertised resources; missing interpreter versions fail helpfully. See W06 and W09.

## System model and review coverage

The shipped optimizer is Markdown interpreted by a host agent. It is not a standalone deterministic prompt optimizer, proof checker, or network service. The CLI installs files or runs regex-based lint. Bash writes user/project skill locations and Cursor rules. The benchmark sends prompts and response text to an operator-selected Ollama endpoint and saves outputs under the repository. The host agent and model provider enforce their own permissions and data handling; the skill text is not a sandbox.
