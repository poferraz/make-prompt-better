# Release checklist

v4.5.1 was released on GitHub and npm on November 7, 2026 (UTC), after its release PR and exact-source main CI passed. Its public installation was verified separately; see the [distribution evidence](npm-publishing.md). Follow the gates below for future versions. Each release channel requires authorization. Keep v4.4.0, v4.5.0, and v4.5.1 immutable.

Changing the benchmark runner's version label changes its source fingerprint. Review that diff before updating `research/benchmark/v4/checkpoint-migration-hashes.json`; never approve arbitrary runner changes just to pass a test. Run the benchmark provenance and rejudge tests to retain the migration guard. Keep historical evidence filenames and their package allowlist entries at the original version.

1. Inspect open issues, pull requests, and the previous release comparison. Keep historical benchmark results labeled with their original version and protocol.
2. Update `package.json`, both plugin manifests, `pyproject.toml`, `CITATION.cff` and its release date, `install.sh`, both skill version labels, `AGENTS.md`, `CLAUDE.md`, the domain-template header, current methodology and trade-off labels, and new benchmark-run metadata. Update the README release link, pinned clone/update commands in the README and guides, and `CHANGELOG.md`. The CLI reads `package.json`; the Cursor rule reads the skill description. Keep historical results, audit transcripts, and unused legacy artwork at their original versions. `scripts/check-release.py` checks the active metadata; its tests deliberately mutate or remove each checked surface.
3. Run `npm run verify` from a full source checkout. It includes structural validation, release metadata, all tests, lint and Bash syntax. Run `./install.sh --dry-run`, the exact validation command in [AGENTS.md](../AGENTS.md), and `./install.sh`; the latter updates local agent installations, so use an isolated temporary home for testing-only work. The fast verification command is not the full release gate.
4. Review `npm pack --dry-run` if distributing the Node CLI. Test installation and repeated installation from a fresh checkout and a six-copy legacy fixture. Query fresh Codex discovery separately from filesystem checks. Use the [npm runbook](npm-publishing.md) for version-specific registry evidence. Credential presence is verified separately from publishing permission.
5. Keep strict branch protection requiring the existing `validate` check. Open a release PR and wait for that check, which requires source verification, every Linux/macOS coverage job, mutation checks, and npm artifact preflight. Merge without bypassing protection, then wait for `validate` on the exact main commit being released. The release guard rejects missing, incomplete, failed, cancelled, skipped or pending main CI evidence; success from an earlier run or attempt does not override a later failure. Scheduled, manually dispatched and PR runs do not replace this main push evidence.
6. Create the version tag and GitHub release targeting that commit, with notes derived from the changelog. State what changed, how it was checked, and what has not been remeasured. Verify the README release link, tag SHA, downloaded source installation, and release status. Attach sanitized discovery evidence with source hashes; do not include home paths, credentials, or private prompts.
7. Obtain separate authorization for npm publication. Dispatch the verified main version of `publish-npm.yml` with `operation=publish`, `release_tag=vX.Y.Z`, and the selected authentication mode. It checks out the immutable source tag and requires successful exact-source main CI. Review the environment job, then inspect registry identity, integrity, provenance, and a clean public installation before adding npm commands to the README. If publication succeeds but verification fails, use `operation=verify-public` with the same release tag; do not publish again. GitHub release creation alone does not trigger npm publication.
8. Re-read the published release and repository About settings. Keep topics factual and link the homepage to current documentation. Share only claims supported by the cited results.

## Current distribution boundaries

Source installation and public npm 4.5.1 are available. Public lifecycle checks passed on Linux and macOS on 2026-11-07; [dated evidence](evidence/2026-11-07/v4.5.1-npm-verification.json) records the scope, bare npx checks, and cross-version upgrade. Public installation needs no token. Publishing credentials belong in a protected maintainer workflow, never in the skill. Future releases need their own public verification. A custom social preview can be uploaded through repository settings; GitHub recommends 1280 by 640 pixels and a PNG, JPG, or GIF under 1 MB.
